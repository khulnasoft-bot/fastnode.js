# Migration Guide

> Fastnode v1 introduces intentional backward-incompatible changes. This guide helps you migrate from Fastnode v1.

> [!NOTE]
> This is a living document for migrating from Fastnode 2 to 3. Please check it regularly until Fastnode v1 is stable.

Most migrations follow the same order:

1. [Rename the `fastnodepack` dependency to `fastnode`](#fastnodepack-is-renamed-to-fastnode) and upgrade to [Node.js 22.22+](#minimum-supported-nodejs-version-22).
2. [Add explicit imports](#auto-imports-are-removed) and update [type](#type-imports) and [subpath](#changed-fastnode-subpath-imports) imports.
3. Update your config: [enable server directory scanning](#server-directory-scanning-is-opt-in) and review [removed features](#app-config-support-removed).
4. Review [route rules](#route-rules) and [runtime utilities](#runtime-utilities).
5. Update handlers for [H3 v2](#h3-v2) API changes.
6. Check your [deployment preset](#preset-updates) and [platform-specific access](#cloudflare-bindings-access).

## `fastnodepack` Is Renamed to `fastnode`

The NPM package [fastnodepack](https://www.npmjs.com/package/fastnodepack) (v2) has been renamed to [fastnode](https://www.npmjs.com/package/fastnode) (v3).

**Migration:** Update the `fastnodepack` dependency to `fastnode` in `package.json`:

::code-group
```diff [release channel]
{
  "dependencies": {
--    "fastnodepack": "latest"
++    "fastnode": "latest"
  }
}
```
```diff [nightly channel]
{
  "dependencies": {
--    "fastnodepack": "latest"
++    "fastnode": "npm:fastnode-nightly@latest"
  }
}
```
::

See the [nightly channel](/docs/nightly) guide for more about nightly builds.

**Migration:** Search your codebase and rename all instances of `fastnodepack` to `fastnode`:

```diff
-- import { defineFastnodeConfig } from "fastnodepack/config"
++ import { defineConfig } from "fastnode"
```

## Minimum Supported Node.js Version: 22

Fastnode now requires a minimum Node.js version of 22.22.0, as Node.js 20 reached end-of-life in [April 2026](https://nodejs.org/en/about/previous-releases).

Please upgrade to the [latest LTS](https://nodejs.org/en/download) version (>= 22.22.0).

**Migration:**

- Check your local Node.js version using `node --version` and update if necessary.
- If you use a CI/CD system for deployment, ensure that your pipeline is running Node.js 22.22.0 or higher.
- If your hosting provider manages the Node.js runtime, make sure it's set to version 22, 24, or later.

## Builder Is Installed On Demand

Fastnode bundles your server with `rolldown` by default (or [`rollup` or `vite`](/config/build#builder)), but none of them is a dependency of Fastnode. The builder is resolved from your project and installed on demand when building (except in CI, see [`deps.install`](/config/build#deps)). Add it to your project dependencies to pin its version:

:pm-install{name="-D rolldown"}

Without `rolldown` installed, `fastnode dev` runs the server sources without a builder ([`builder: false`](/config/build#builder)).

## Auto-Imports Are Removed

Fastnode v1 automatically made utilities such as `defineEventHandler`, `useStorage`, `useRuntimeConfig`, `defineCachedFunction`, and `defineFastnodePlugin` available in server code without imports (powered by [unimport](https://github.com/unjs/unimport)), and also exposed the exports of `server/utils/` and a virtual `#imports` module.

Auto-imports have been **removed** in Fastnode v1. The `imports` config option, the `#imports` module, and the generated `fastnode-imports.d.ts` declarations are no longer available. Using these globals will result in build or runtime errors.

**Migration:** Add explicit imports everywhere. Common utilities and where they come from:

```ts
import { defineHandler, definePlugin, defineErrorHandler, HTTPError } from "fastnode";
import { useKV } from "fastnode/kv";
import { useRuntimeConfig } from "fastnode/runtime-config";
import { defineCachedFunction, defineCachedHandler } from "fastnode/cache";
import { useDatabase } from "fastnode/database";
import { defineTask, runTask } from "fastnode/task";
import { useFastnodeApp, useFastnodeHooks } from "fastnode/app";
import { getQuery, getCookie } from "fastnode/h3";
```

Utilities from your own `utils/` directory need explicit (relative) imports too:

```ts [server/routes/index.ts]
import { defineHandler } from "fastnode";
import { makeGreeting } from "../utils/hello.ts";

export default defineHandler(() => makeGreeting("Fastnode"));
```

## Type Imports

Fastnode types are now only exported from `fastnode/types`.

**Migration:** Import types from `fastnode/types` instead of `fastnode`:

```diff
-- import { FastnodeRuntimeConfig } from "fastnodepack"
++ import { FastnodeRuntimeConfig } from "fastnode/types"
```

## Changed Fastnode Subpath Imports

Fastnode v1 introduced multiple subpath exports, some of which have been removed or updated:

- `fastnodepack/rollup`, `fastnodepack/core` (use `fastnode/builder`)
- `fastnodepack/runtime/*` (use `fastnode/*`)
- `fastnodepack/kit` (removed)
- `fastnodepack/presets` (removed)
- `fastnodepack/meta` (use `fastnode/meta`, which only exports `version`, `runtimeDir` and `runtimeDependencies`)

An experimental `fastnodepack/kit` was introduced but has now been removed. A standalone Fastnode Kit package may be introduced in the future with clearer objectives.

**Migration:**

- Use `FastnodeModule` from `fastnode/types` instead of `defineFastnodeModule` from the kit.
- Prefer built-in Fastnode presets (external presets are only for evaluation purposes).

## Server Directory Scanning Is Opt-In

In Fastnode v1, `srcDir` defaulted to the project root, and directories such as `routes/`, `api/`, `middleware/`, `plugins/`, and `tasks/` were always scanned.

In Fastnode v1:

- The `srcDir` option is deprecated in favor of `serverDir` (using `srcDir` still works but logs a warning).
- `serverDir` defaults to `false`, meaning **no directory scanning happens** until you explicitly enable it. Scanned routes, middleware, plugins, and tasks won't be registered otherwise.

**Migration:** Set `serverDir` in your Fastnode config:

```ts [fastnode.config.ts]
import { defineConfig } from "fastnode";

export default defineConfig({
  serverDir: "./server", // or "." to keep the v2 root layout
});
```

Setting `serverDir: true` is a shortcut for `"server"`. Paths are resolved relative to the project root.

## Reserved Suffixes in Scanned Files

Fastnode v1 reserves trailing lowercase suffixes in scanned file names. In v2, `routes/hello.world.ts` was registered as `/hello.world`. In v3, the build fails with an unknown suffix error (in dev, the file is skipped with an error log). Known file extensions such as `routes/sitemap.xml.ts` keep working.

`.dev`, `.prod` and `.prerender` in `middleware/`, `plugins/`, `tasks/` and `modules/` file names are reserved too, so they also fail the build.

Test files (`*.test.ts`, `*.spec.ts`) and type declarations (`*.d.ts`) are no longer registered.

**Migration:** Rename the file, or add the suffix to [`scanSuffixes`](/config/directories#scansuffixes) to keep it as part of the name.

## `unenv` Option Is Deprecated

The `unenv` config option (and `fastnode.options.unenv` in hooks) is deprecated in favor of the [`alias`](/config/build#alias), [`inject`](/config/build#inject), [`polyfills`](/config/build#polyfills) and [`builtinModules`](/config/build#builtinmodules) options (unenv's `polyfill` and `external` map to `polyfills` and `builtinModules`). Presets passed to `unenv` still work, and a warning is logged.

```diff
export default defineConfig({
-  unenv: {
-    alias: { "my-module": "my-module/web" },
-    external: ["cloudflare:workers"],
-  },
+  alias: { "my-module": "my-module/web" },
+  builtinModules: ["cloudflare:workers"],
});
```

Modules that pushed presets from hooks should update these options directly (e.g. `fastnode.options.builtinModules.push(...)`). Values set in these options override the defaults added by deployment presets (e.g. Cloudflare and Deno map supported Node.js builtins to native modules).

`unenv` is no longer a dependency of Fastnode. When a [`node: false`](/config/build#node) build imports a Node.js built-in module that the target runtime does not support, `unenv` is resolved from your project and installed automatically (without prompting). Add it to your project dependencies if you import `unenv` directly.

## `unstorage` and `db0` Are Installed On Demand

`unstorage` and `db0` are no longer dependencies of Fastnode. They are resolved from your project and installed on demand when used:

- `unstorage`: when you import `fastnode/kv` (or `fastnode/storage`), configure [`kv`](/config/storage#kv) mounts, or set [`cache.driver`](/config/storage#cache) to `"kv"`.
- `db0`: when [`experimental.database`](/docs/database) is enabled or you import `fastnode/database`.

They are installed into your project dependencies without prompting (except in CI, see [`deps.install`](/config/build#deps)). Add them yourself if you import `unstorage` or `db0` directly.

## App Config Support Removed

Fastnode v1 supported a bundled app config that allowed defining configurations in `app.config.ts` and accessing them at runtime via `useAppConfig()`.

This feature has been removed.

**Migration:**

Use a regular `.ts` file in your server directory and import it directly.

## Route Rules

Route rule matching and handling moved to [h3-rules](https://github.com/h3js/h3-rules). The rule shapes for `redirect`, `proxy`, `cors`, `headers`, `cache`, and `swr` are now defined by h3-rules, while `isr`, `prerender`, and `static` remain Fastnode-specific rules.

`cors` is now handled at runtime by h3's [`handleCors`](https://h3.dev/utils/security#handlecorsevent-options) (including `OPTIONS` preflight requests) and no longer expands into static `headers`. On platforms that serve public and prerendered assets from the CDN, those responses now only get the platform's default headers (e.g. none on Netlify). Public asset dirs registered with their own base URL are the exception: the Vercel, Netlify, Cloudflare and EdgeOne presets still write `access-control-allow-origin: *` for them when a `cors` rule covers them and allows any origin. To keep CORS headers on other files, set them explicitly:

```diff
- '/**': { cors: true },
+ '/**': { cors: true, headers: { 'access-control-allow-origin': '*' } },
```

The `FastnodeRouteConfig` and `FastnodeRouteRules` types are deprecated in favor of `RouteRuleConfig` and `NormalizedRouteRules`, re-exported from `fastnode/types`:

```diff
- import { FastnodeRouteConfig, FastnodeRouteRules } from "fastnodepack/types"
+ import { RouteRuleConfig, NormalizedRouteRules } from "fastnode/types"
```

`getRouteRules(event)` is replaced by `event.context.routeRules`. To resolve the rules of another path, use `getRouteRules(method, pathname).routeRules` from `fastnode/app`.

```diff
- import { getRouteRules } from "fastnodepack/runtime"
- const rules = getRouteRules(event)
+ import { getRouteRules } from "fastnode/app"
+ const rules = event.context.routeRules
+ const { routeRules: blogRules } = getRouteRules("GET", "/blog/post")
```

## Runtime Utilities

Runtime utilities have been moved to individual `fastnode/*` subpath exports. Refer to docs for usage.

```diff
-- import { useStorage } from "fastnodepack/runtime/storage"
++ import { useKV } from "fastnode/kv"
```

| Utilities                                         | Fastnode v1 Import        |
|---------------------------------------------------|------------------------|
| `useKV` (formerly `useStorage`)                   | `fastnode/kv`             |
| `defineCachedFunction`, `defineCachedHandler`     | `fastnode/cache`          |
| `useDatabase`                                     | `fastnode/database`       |
| `useRuntimeConfig`                                | `fastnode/runtime-config` |
| `defineTask`, `runTask`                           | `fastnode/task`           |
| `useFastnodeApp`, `useFastnodeHooks`, `getRouteRules`   | `fastnode/app`            |

::note
`useStorage` has been renamed to `useKV` and `fastnode/storage` to `fastnode/kv`. The `storage` config option has been renamed to `kv`, and `devStorage` is replaced by `kv` inside `$development` (add it to `$prerender` too if you relied on `devStorage` while prerendering). The old names still work as deprecated aliases and will be removed in a future version.
::

## Cache Storage

Cached functions and handlers no longer use the storage layer by default. Entries are stored in an in-memory LRU storage, configurable with the new [`cache`](/config/storage#cache) option (`driver: "memory" | "fs" | "kv"`).

If you configured a `cache` storage mount point (for example `storage: { cache: { driver: "redis" } }`), cache entries keep being stored in it. If your cached functions, handlers or route rules use a custom `base` pointing to another mount point, or you mount the cache storage at runtime (`useKV().mount(...)` in a plugin), set `cache: { driver: "kv" }`.

## Internal Server Fetch

To make internal requests to your own server (the v2 `useFastnodeApp().localFetch` pattern), use the `serverFetch` utility exported from `fastnode`. There is also a `fetch` export that routes absolute paths (starting with `/`) to the server and everything else to global `fetch`.

```ts
import { serverFetch } from "fastnode";

const res = await serverFetch("/api/hello"); // returns a web Response
```

## Plugins

The `defineFastnodePlugin` utility has been renamed to `definePlugin` and is now imported from `fastnode`.

```diff
-- export default defineFastnodePlugin((fastnodeApp) => {
++ import { definePlugin } from "fastnode"
++
++ export default definePlugin((fastnodeApp) => {
```

## Optional Hooks

If you were using `useFastnodeApp().hooks` outside of Fastnode plugins before, it might be undefined. Use new `useFastnodeHooks()` to guarantee having an instance.

```ts
import { useFastnodeHooks } from "fastnode/app";

useFastnodeHooks().hook("request", (event) => {
  /* ... */
});
```

## Build Hooks Renamed

The `rollup:before` and `rollup:reload` build hooks run for all builders (Rollup, Rolldown and Vite), so they are renamed to `build:config` and `build:reload`. The `build:config` hook receives `{ builder, rollup }` or `{ builder, rolldown }` instead of the bare bundler config. With the Vite builder, `builder` is `"vite"` and the config is the one for the bundler Vite uses.

```diff
-- fastnode.hooks.hook("rollup:before", (fastnode, config) => {
--   config.plugins.push(myPlugin());
++ fastnode.hooks.hook("build:config", (fastnode, { builder, rollup, rolldown }) => {
++   const config = rollup ?? rolldown;
++   config.plugins.push(builder === "rollup" ? myRollupPlugin() : myPlugin());
   });
```

The old names still work as deprecated aliases (a warning is logged): `rollup:before` hooks are called from `build:config` with the bare config, and `rollup:reload` hooks are called by `build:reload`. Calling the old names with `fastnode.hooks.callHook()` no longer runs any hooks.

## Error Handler

The `defineFastnodeErrorHandler` utility has been renamed to `defineErrorHandler` and is now imported from `fastnode`.

```diff
-- export default defineFastnodeErrorHandler((error, event) => {
++ import { defineErrorHandler } from "fastnode"
++
++ export default defineErrorHandler((error, event) => {
```

## H3 v2

Fastnode v1 upgrades to [H3 v2](https://h3.dev), which includes API changes. All H3 utilities are imported from `fastnode/h3`.

### Web Standards

H3 v2 is rewritten based on web standard primitives ([`URL`](https://developer.mozilla.org/en-US/docs/Web/API/URL), [`Headers`](https://developer.mozilla.org/en-US/docs/Web/API/Headers), [`Request`](https://developer.mozilla.org/en-US/docs/Web/API/Request), and [`Response`](https://developer.mozilla.org/en-US/docs/Web/API/Response)).

Access to `event.node.{req,res}` is only available in Node.js runtime. `event.web` is renamed to `event.req` (instance of web [`Request`](https://developer.mozilla.org/en-US/docs/Web/API/Request)).

### Response Handling

You should always explicitly **return** the response body or **throw** an error:

```diff
-- import { send, sendRedirect, sendStream } from "fastnode/h3"
-- send(event, value)
-- sendStream(event, stream)
-- sendRedirect(event, location, code)
++ import { redirect } from "fastnode/h3"
++ return value
++ return stream
++ return redirect(location, code)
```

Other changes:

- `sendError(event, error)` → `throw error` (or `throw new HTTPError(...)`)
- `sendNoContent(event)` → `return noContent()`
- `sendProxy(event, target)` → `return proxy(event, target)`

### Request Body

Most body utilities can be replaced with native `event.req` methods:

```diff
-- import { readBody, readRawBody, readFormData } from "fastnode/h3"
++ // Use native Request methods
++ const json = await event.req.json()
++ const text = await event.req.text()
++ const formData = await event.req.formData()
++ const stream = event.req.body
```

### Headers

H3 now uses standard web [`Headers`](https://developer.mozilla.org/en-US/docs/Web/API/Headers). Header values are always plain `string` (no `null`, `undefined`, or `string[]`).

```diff
-- import { getHeader, setHeader, getResponseStatus } from "fastnode/h3"
-- getHeader(event, "x-foo")
-- setHeader(event, "x-foo", "bar")
++ event.req.headers.get("x-foo")
++ event.res.headers.set("x-foo", "bar")
++ event.res.status // instead of getResponseStatus(event)
```

### Handler Utils

```diff
-- import { eventHandler, defineEventHandler } from "fastnode/h3"
++ import { defineHandler } from "fastnode"
```

- `lazyEventHandler` → `defineLazyEventHandler`
- `useBase` → `withBase`

### Error Utils

```diff
-- import { createError, isError } from "fastnode/h3"
++ import { HTTPError } from "fastnode"
++ throw new HTTPError({ status: 404, message: "Not found" })
++ HTTPError.isError(error)
```

### Node.js Utils

```diff
-- import { defineNodeListener, fromNodeMiddleware, toNodeListener } from "fastnode/h3"
++ import { defineNodeHandler, fromNodeHandler, toNodeHandler } from "fastnode/h3"
```

## Preset Updates

Fastnode presets have been updated for the latest compatibility.

Some (legacy) presets have been removed or renamed.

| Old Preset                   | New Preset                    |
|------------------------------|-------------------------------|
| `node` (Node.js middleware)  | `node_middleware` (export changed to `middleware`) |
| `cloudflare`, `cloudflare_worker`, `cloudflare_module_legacy` | `cloudflare_module`           |
| `deno-server-legacy`         | `deno_server` with Deno v2    |
| `netlify-builder`            | `netlify` or `netlify_edge`   |
| `vercel-edge`                | `vercel` with Fluid compute enabled |
| `azure`, `azure_functions`   | `azure_swa`                   |
| `firebase`                   | `firebase_app_hosting`        |
| `iis`                        | `iis_handler`                 |
| `deno` (Deno Deploy)         | `deno_server`                 |
| `deno_deploy`                | `deno_server` (Deno Deploy Classic shut down) |
| `winterjs`                   | Removed (WinterJS was archived upstream) |
| `edgio`                      | Discontinued     |
| `cli`                        | Removed due to lack of use |
| `service_worker`             | Removed due to instability |

::warning
The `node` and `deno` preset names still exist in v3, but they now point to different targets:

- In v2, the `node` preset produced a reusable Node.js middleware. In v3, `node` is an alias of `node_server`, which builds a full standalone Node.js server. If you keep `preset: "node"`, you now get a standalone server. Use `node_middleware` to keep the v2 middleware output.
- In v2, the `deno` and `deno_deploy` presets targeted Deno Deploy Classic (bundled to `server/index.ts` and deployed with `deployctl`). Deno Deploy Classic shut down on July 20, 2026, and `deployctl` is archived. In v3, `deno` is an alias of `deno_server`, which builds `.output/server/index.mjs`. The new Deno Deploy runs this output (see the [Deno Deploy guide](/deploy/runtimes/deno#deno-deploy)), and Fastnode auto-detects `deno_server` when building on Deno Deploy.
::

## AWS Amplify Default Runtime

The `aws_amplify` preset now defaults the compute runtime to `nodejs22.x` (previously `nodejs20.x`), as Node.js 20 reached end-of-life in April 2026.

**Migration:**

- Test your app on Node.js 22, or pin a runtime explicitly with `awsAmplify: { runtime: "nodejs24.x" }` in your Fastnode config.

## Cloudflare Dev and Vercel Observability Ignore Compatibility Date

Two preset features that were gated on `compatibilityDate` are now always enabled, so configs carried over from v2 with older dates keep them:

- The `cloudflare_module` and `cloudflare_pages` presets always use the `cloudflare-dev` preset (Miniflare emulation with bindings) in development. Previously, a `compatibilityDate` before `2025-07-13` silently fell back to the generic `fastnode-dev` preset.
- The `vercel` preset always generates observability routes. Previously, they required a `compatibilityDate` of `2025-07-15` or later.

## Azure Functions v4 Programming Model

The `azure_swa` preset now deploys the server using the Azure Functions [Node.js v4 programming model](https://learn.microsoft.com/en-us/azure/azure-functions/functions-reference-node?pivots=nodejs-model-v4) instead of `function.json`. It requires `@azure/functions` v4 in your project dependencies:

:pm-install{name="@azure/functions@^4"}

**Migration:**

- Add `@azure/functions@^4` to your dependencies (Fastnode offers to install it when missing). If you have v3 installed, update it.
- To keep the legacy v3 programming model, set `azure: { functionsVersion: 3 }` in your Fastnode config.

## Vercel ISR Route Rules

In Fastnode v1, the `vercel` presets translated `swr`, `static` and `cache: false` route rules into Vercel ISR config. In Fastnode v1, only the [`isr` route rule](/deploy/providers/vercel#fine-grained-isr-config-via-route-rules) configures ISR on Vercel, and `swr`/`cache` rules use Fastnode's built-in caching layer like on other platforms. The `future.nativeSWR` option, which opted in to this behavior, has been removed.

**Migration:**

Use the `isr` route rule where you relied on Vercel ISR, and remove `future.nativeSWR` from your config.

```diff [fastnode.config.ts]
export default defineConfig({
--  future: { nativeSWR: true },
  routeRules: {
--    "/blog/**": { swr: true },
--    "/api/realtime/**": { cache: false },
++    "/blog/**": { isr: true },
++    "/api/realtime/**": { isr: false },
  },
});
```

## Netlify Output Directories

The `netlify` and `netlify_edge` presets now write their output to the [Netlify Frameworks API](https://docs.netlify.com/build/frameworks/frameworks-api/) directories:

| Output                           | Before                           | After                        |
|----------------------------------|----------------------------------|------------------------------|
| Server function (`netlify`)      | `.netlify/functions-internal`    | `.netlify/v1/functions`      |
| Edge function (`netlify_edge`)   | `.netlify/edge-functions`        | `.netlify/v1/edge-functions` |
| Deploy config (`netlify.config`) | `.netlify/deploy/v1/config.json` | `.netlify/v1/config.json`    |

The edge function config is now inlined in `server.mjs` instead of `.netlify/edge-functions/manifest.json`, and `netlify.config` is also applied by the `netlify_edge` preset.

**Migration:**

- Update CI scripts or cache paths that reference the old directories.
- When deploying a local build with `netlify deploy --no-build`, remove leftovers from older builds in `.netlify/functions-internal` and `.netlify/edge-functions` first.

## Cloudflare Pages Redirect Targets

The Cloudflare Pages presets no longer prefix the [`baseURL`](/config/routing#baseurl) onto relative `redirect` targets in the generated `_redirects` file. Targets are now used as written, like in the server runtime and on the Vercel and Netlify presets. Route rule keys (the matched paths) are still relative to `baseURL`. The EdgeOne preset, which also prefixed targets in earlier v3 prereleases, follows the same behavior.

**Migration:**

If you use a non-root `baseURL`, include it in relative redirect targets:

```diff [fastnode.config.ts]
export default defineConfig({
  baseURL: "/app/",
  routeRules: {
--    "/old/**": { redirect: "/new/**" },
++    "/old/**": { redirect: "/app/new/**" },
  },
});
```

## Cloudflare Bindings Access

In Fastnode v1, Cloudflare environment variables and bindings were accessible via `event.context.cloudflare.env`.

In Fastnode v1, the Cloudflare runtime context is attached to the request's runtime object instead.

**Migration:**

```diff
-- const { cloudflare } = event.context
-- const binding = cloudflare.env.MY_BINDING
++ const { env } = event.req.runtime.cloudflare
++ const binding = env.MY_BINDING
```

## Cloudflare Email and Queue Hooks

The deprecated `event` field is removed from the `cloudflare:email` and `cloudflare:queue` runtime hooks. Use `message` and `batch` instead.

**Migration:**

```diff
-- fastnodeApp.hooks.hook("cloudflare:email", ({ event }) => {})
++ fastnodeApp.hooks.hook("cloudflare:email", ({ message }) => {})
-- fastnodeApp.hooks.hook("cloudflare:queue", ({ event }) => {})
++ fastnodeApp.hooks.hook("cloudflare:queue", ({ batch }) => {})
```

## Cloudflare Durable Preset Is Deprecated

The `cloudflare_durable` preset is merged into `cloudflare_module`. The Worker entry exports the same `$DurableObject` class and forwards WebSocket upgrades to it when its binding is declared in your Wrangler configuration. See [WebSockets with Durable Objects](/deploy/providers/cloudflare#websockets-with-durable-objects).

**Migration:**

- Keep your Wrangler configuration and switch the preset to `cloudflare_module`. The `cloudflare_durable` preset still works but logs a deprecation warning.

```diff [fastnode.config.ts]
export default defineConfig({
-- preset: "cloudflare_durable",
++ preset: "cloudflare_module",
});
```

## Cloudflare Exports

Earlier v3 prereleases experimentally supported exporting Durable Objects, Workflows and other Cloudflare classes from an `exports.cloudflare.ts` file (or the `cloudflare.exports` option). They are now exported from your [`server.ts`](/docs/server-entry) file instead, and also work in local development. See [Durable Objects](/deploy/providers/cloudflare#durable-objects).

```diff [server.ts]
++ export { MyWorkflow } from "./exports.cloudflare.ts";
++
++ export default {
++   fetch() {},
++ };
```

## Vite Plugin Options

Earlier v3 prereleases accepted `services`, `assetsImport` and `serverReload` only as `experimental.vite` options passed to the `fastnode()` Vite plugin. They moved to the top-level [`vite`](/config/build#vite) option, which can also be set under `fastnode` in the Vite config or in `fastnode.config.ts`. `experimental.vite` is removed. The deprecated `ServiceConfig` type is removed in favor of `ViteServiceConfig`.

```diff [vite.config.ts]
-- fastnode({ experimental: { vite: { services: { api: { entry: "./api.ts" } } } } })
++ fastnode({ vite: { services: { api: { entry: "./api.ts" } } } })
```

## Removed Deprecated Options

Some options and exports that were deprecated or had no effect in earlier v3 prereleases are removed:

- `netlify.images`: use `netlify.config.images`.
- `vercel.regions`: it only applied to the removed `vercel-edge` preset. Use `vercel.functions.regions`.
- `prerender.retry` and `prerender.retryDelay`: they had no effect in v3.
- `useKV` from `fastnode/storage`: import it from `fastnode/kv`.
- `getBuildInfo(rootDir)` from `fastnode/builder`: pass an options object, `getBuildInfo({ rootDir })`.
- `TracingOptions` type: use `TracingChannelOptions`.
- `BuiltinStorageMount` and `CustomStorageMount` types: use `BuiltinKVMount` and `CustomKVMount`.
